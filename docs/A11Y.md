# Auditoria de acessibilidade — WCAG 2.1 nível AA

**Projeto:** LOLA Aço Inox & Acessórios (loja pt-BR de semijoias em aço inox)
**Escopo:** os 12 modais/drawers do frontend + navegação por teclado da sacola e do
checkout, contraste real das cores do tema, alvos de clique, textos alternativos de
imagem e respeito a `prefers-reduced-motion`.
**Método:** leitura estática de todo o código-fonte de `src/` com rastreio de caminhos de
foco, com cálculo de contraste WCAG (luminância relativa, fórmula de WCAG 2.x) sobre os
valores hexadecimais efetivamente usados. Nada foi corrigido: cada achado traz o
critério violado, a severidade e a correção proposta. A remediação pertence à onda 2
(`fe-a11y`).

## Sumário executivo

| Métrica | Valor |
|---|---|
| Modais/drawers auditados | 12 |
| Com `role="dialog"` | 12 de 12 |
| Com `aria-modal` correto | 11 de 12 (o chatbot o omite por ser não-modal — correto) |

| Achados totais (F01–F39) | 39 |

| Severidade alta | 14 |

| Severidade baixa | 6 |

**O achado conhecido (sem trap e sem `Escape`) é a ponta do iceberg.** O detalhamento
abaixo mostra que os 12 modais violam o mesmo conjunto de critérios de forma sistemática
— e acrescenta quatro achados que o teste manual rápido não pegaria: o
`OrderSuccessModal` é uma armadilha total (não fecha nem por backdrop nem por `Escape`
nem tem botão ✕), os 9 rótulos do formulário de endereço do checkout são órfãos, o
dourado `#C49A5A` é usado como *cor de texto* em 123 lugares com contraste de 2,36:1, e
as fotos de produto são reutilizadas com nomes divergentes, tornando o `alt` de 7
produtos ativamente enganoso.

**Severidade:** `crítica` = impede ou trava tarefas inteiras para leitor de tela/teclado;
`alta` = bloqueia uma tarefa específica; `média` = dificulta ou exige esforço extra;
`baixa` = desconforto ou dívida de qualidade.

## 1. O sistema de modais como um todo

O projeto tem dois esqueletos de modal, ambos montados condicionalmente
(`if (!isOpen) return null`) e ambos incompletos:

- **Esqueleto A — painel lateral (drawer):** `CartDrawer.tsx:34`,
  `FavoritesModal.tsx:29`, `MobileFilterDrawer.tsx:32`.
- **Esqueleto B — caixa centralizada:** `ClearCartModal.tsx:18`, `CouponModal.tsx:45`,
  `ShippingCalculatorModal.tsx:48`, `InfoModal.tsx:24`, `WhatsAppModal.tsx:29`,
  `ProductDetailModal.tsx:55`, `OrderSuccessModal.tsx:24`, `ProductLightboxModal.tsx:47`,
  `ChatbotAssistente.tsx:157`.

Nenhum dos dois esqueletos guarda o elemento que abriu, move o foco para dentro do
diálogo, prende o `Tab` ou trata `Escape`. O único código de teclado de diálogo do
projeto inteiro está em `ProductLightboxModal.tsx:21-34`.

### 1.1 Caminho exato de tabulação que escapa (exemplo reproduzível: sacola)

Para provar que `aria-modal="true"` não tem efeito prático sem trap, eis o percurso real
do teclado, com arquivo:linha. A sacola abre pelo botão `SiteHeader.tsx:306-317`
(`onOpenCart`). O estado é gerido em `App.tsx:85` e o drawer é renderizado em
`App.tsx:619` — **depois** do rodapé (`App.tsx:616`), ou seja, no fim do documento.

1. Usuário ativa "Sacola de compras" (`SiteHeader.tsx:306`). O drawer abre, mas **o foco
   permanece no botão do cabeçalho**, que está atrás do overlay preto — `aria-modal` não
   remove nada da ordem de tabulação; ele é só uma instrução ignorada por teclados
   reais. Critério **2.4.3 Focus Order**.
2. `Tab` → próximo focável do cabeçalho: botão de menu mobile (`SiteHeader.tsx:320`).
   Continua atrás do overlay.
3. `Tab` repetido → percorre todo o site atrás do overlay (busca
   `SiteHeader.tsx:221`, favoritos `SiteHeader.tsx:283`, hero `HeroCarousel.tsx:80`…).
   Critério **2.4.3** e **2.1.2 Sem bloqueio de teclado**.
4. Suponha que o usuário consiga entrar no drawer (clique ou many `Shift+Tab`). Ordem
   interna: fechar (`CartDrawer.tsx:52`) → diminuir quantidade (`:130`) → aumentar
   (`:140`) → remover (`:149`) → repete por item → "Ver Sacola" (`:189`) → "Finalizar"
   (`:199`).
5. Um `Tab` a partir de "Finalizar" (`CartDrawer.tsx:199-205`) sai do diálogo: o próximo
   focável do DOM é do outro lado do documento, e o foco cai na barra do navegador e
   depois no logo (`SiteHeader.tsx:91`) — tudo visually coberto pela camada
   `bg-black/60` (`CartDrawer.tsx:36-39`). Critério **2.1.2** (bloqueio de foco) e
   **2.4.3**. **Achado F01 (crítica).**

O mesmo caminho vale para os outros 11: em todos, o `Tab` sai do diálogo sem encontrar
borda.

### 1.2 `Escape`

`grep` por `Escape` em `src/` devolve **um** resultado: `ProductLightboxModal.tsx:24`.
Os outros 11 diálogos só fecham por clique no backdrop (quando existe) ou por botão.
**Achado F02 (crítica).**

### 1.3 Devolução de foco

Nenhum componente guarda `document.activeElement` ao abrir. Ao fechar, o componente
retorna `null`, o nó some do DOM e o navegador joga o foco para `<body>`. Quem navega por
teclado e abre a sacola para trocar a quantidade de um item termina, ao fechar, no topo
da página. Critério **2.4.3 Focus Order** (e, no caso do checkout, perda de contexto de
tarefa). **Achado F03 (crítica).**

### 1.4 Foco inicial e rótulo do diálogo

Dois defects que atravessam os 12:

- **Foco inicial (F04, alta).** Só o chat move o foco para dentro ao abrir
  (`ChatbotAssistente.tsx:52-57`). Nos outros 11, o foco fica no gatilho — que está
  atrás do overlay — ou no `<body>`. O leitor de tela ouve a página de fundo, não o
  diálogo. Critério **2.4.3**.
- **Rótulo do diálogo (F06, alta).** `aria-labelledby` não existe em nenhum arquivo do
  projeto (`grep aria-labelledby src/` → zero). Só 2 diálogos têm nome acessível de
  outra forma: o lightbox por `aria-label` (`ProductLightboxModal.tsx:51`) e o chat por
  `aria-label` (`ChatbotAssistente.tsx:159`). Os outros 10 declaram `role="dialog"` sem
  nome: o leitor de tela anuncia apenas "diálogo". Critério **4.1.2 Name, Role, Value**.

## 5. Textos alternativos e semântica de imagem

`grep` por `alt={` em `src/` — 21 imagens renderizadas com alt dinâmico, zero com `alt`
ausente (bom), mas o conteúdo é o problema:

1. **`alt={product.name}` em toda imagem de produto** (`CartDrawer.tsx:111`,
   `FavoritesModal.tsx:87`, `ProductDetailModal.tsx:80`, `EarringProductCard.tsx:65,158`,
   `FeaturedProductsSection.tsx:128`, `SiteHeader.tsx:258`, `CheckoutPage.tsx:398`,
   `CheckoutOrderSummary.tsx:97`, `RelatedProductsSection.tsx:97`,
   `CartItemCard.tsx:33`, `ChatbotAssistente.tsx:195`, `CartPage.tsx:219`).
   Duas falhas em uma frase:
   - **Redundância:** o nome do produto costuma estar visível a alguns pixels do `alt`
     (título do card). Leitor de tela ouve o nome duas vezes.
   - **Imprecisão/enganosidade:** as fotos são reutilizadas entre produtos com nomes
     diferentes — `product_earrings_1791578709776.jpg` serve a **7** produtos distintos
     (`mockData.ts:83,180,204,230,290…`), incluindo "Brinco Argola Lisa" e "Argola
     Prateada Espelhada". O `alt` afirma que a imagem é da peça X quando ela é uma foto
     genérica de argola. Para uma loja de semijoias, a descrição visual (cor, formato,
     tamanho, se está no ouvido) é exatamente a informação que falta. Critério
     **1.1.1 Non-text Content**.
2. **`alt="Foto detalhe N"`** — genérico de verdade (`ProductDetailsSection.tsx:42`).
3. **Hero:** `alt={currentSlide.title}` (`HeroCarousel.tsx:43`) duplica o `h1` visível
   (`:69-71`) — imagem de fundo com gradiente; o alt correto aqui é `alt=""`
   (decorativa). Nota: os 3 slides usam a mesma foto (`mockData.ts:56,64,72`).
4. **Banner do checkout:** `alt="Joias Lola Checkout"` (`CheckoutPage.tsx:240`) —
   keyword stuffing; imagem coberta por gradiente `95%→30%`, é decorativa → `alt=""`.
5. **Lightbox:** principal `alt={\`${productName} - foto ${n}\`}`
   (`ProductLightboxModal.tsx:86`) — baseado em contador, não descreve; miniaturas
   `alt=""` ✔ (`:114`) com botão rotulado ✔ — **padrão correto, adotar como referência**.

**Correção proposta (F27 alta, F28 média):** (a) `Product` ganha campo `imageAlt` descritivo por
peça ("Argola dourada lisa de 3 cm, foto de frente"), preenchido por quem monta o

## 9. `useDialogA11y` — hook único para os 12 diálogos

O inventário mostra que as 12 implementações repetem as mesmas seis propriedades
quebradas. A onda 2 (`fe-a11y`) deve extrair uma única fonte de verdade:
`src/hooks/useDialogA11y.ts` (território já reservado a ele na MANIFEST).

### 9.1 API sugerida

```ts
import { useRef } from 'react';

export interface UseDialogA11yOptions {
  /** Controla montagem, como hoje (isOpen). */
  isOpen: boolean;
  /** Chamado pelo Escape, pelo backdrop (se ligado) e pelo ✕ do hook. */
  onClose: () => void;
  /** Papel do diálogo. `alertdialog` para confirmações destrutivas. Default: 'dialog'. */
  role?: 'dialog' | 'alertdialog';
  /**
   * false para janelas não modais (chat flutuante): sem aria-modal,
   * sem trap, sem fechar no backdrop, mas ainda com foco inicial/devolução.
   * Default: true.
   */
  isModal?: boolean;
  /** Fecha com clique no backdrop. Default: true. Ignorado se isModal=false. */
  closeOnBackdrop?: boolean;
  /**
   * Elemento a focar ao abrir. Default: primeiro focável do contêiner
   * (ou o próprio contêiner com tabIndex=-1, para diálogos sem focável inicial
   * como o OrderSuccessModal).
   */
  initialFocusRef?: React.RefObject<HTMLElement | null>;
  /** Devolve foco ao gatilho ao fechar. Default: true. */
  returnFocus?: boolean;
  /** Rola o diálogo para a visão ao abrir. Default: true. */
  scrollIntoView?: boolean;
}

export function useDialogA11y(options: UseDialogA11yOptions): {
  /** Aplicar no elemento raiz do diálogo. */
  dialogProps: {
    ref: (el: HTMLElement | null) => void;
    role: 'dialog' | 'alertdialog';
    'aria-modal': true | undefined;
    'aria-labelledby': string | undefined;
    onKeyDown: (e: React.KeyboardEvent) => void; // Escape
    tabIndex: -1;
  };
  /** Aplicar no backdrop. */
  backdropProps: { onClick: () => void; 'aria-hidden': true };
  /** Aplicar no <h2>/<h3> do título. Estável entre renders. */
  titleId: string;
  /** Útil para o consumidor focar algo específico pós-abertura (ex.: input do cupom). */
  containerRef: React.RefObject<HTMLDivElement | null>;
};
```

### 9.2 Comportamento interno (especificação para implementar)

1. **Abertura:** guarda `document.activeElement` num `useRef` (se `returnFocus`);
   agenda `requestAnimationFrame` para mover o foco para `initialFocusRef` ?? primeiro
   focável do contêiner ?? o contêiner (`tabIndex={-1}`); trava `document.body` com
   `overflow: hidden` (fundo não rola atrás do drawer).
2. **Trap:** listener de `keydown` no contêiner: em `Tab`, coleta
   `button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])` visíveis do
   contêiner e cicla (primeiro→último, último→primeiro, inclusive com `Shift+Tab`).
   `Escape` chama `onClose`. Listener global só enquanto `isOpen` (hoje só o lightbox
   faz isso em `ProductLightboxModal.tsx:32`).
3. **Backdrop:** `div` com `aria-hidden="true"` e `onClick` condicional — mantendo a
   composição visual atual (`fixed inset-0 bg-black/60 backdrop-blur-xs`).
4. **Fechamento:** remove listeners, devolve foco ao gatilho guardado (com
   `el?.focus({ preventScroll: true })`), reabilita scroll do body.
5. **Bom cidadão:** quando o diálogo está aberto, aplica `inert` (ou `aria-hidden` como
   fallback) nos irmãos de `#root` — é a defesa em profundidade que mata o caminho de
   fuga do §1.1 mesmo que um consumidor esqueça o trap.
